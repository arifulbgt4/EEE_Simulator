# ADR-0004: Versioned `.eesim` Project Format

- Status: Accepted
- Date: 2026-07-11
- Decision owners: Project maintainers
- Related requirements: `REQ-005`, `REQ-006`, `REQ-013`, `REQ-024`, `REQ-031`, `REQ-037`, `REQ-038`

## Context

A project must preserve its schematic, hierarchy, component models, simulation configuration, waveforms or result references, measurements, testbenches, version history, comments, and documentation. [Source PDF, pp. 31-32]

Portable projects also need deterministic migration, offline use, stable model identity, and a representation suitable for review in version control.

## Decision

- `.eesim` shall be the canonical versioned project archive.
- Each archive shall contain `manifest.json` and versioned sections for schematic hierarchy, component references, custom models, stimuli, testbenches, measurements, project documentation, and user assets.
- Generated results may be embedded only when declared by the manifest; otherwise the archive stores immutable result references and provenance.
- Every persisted public object shall have a stable identifier and schema version.
- Unknown required fields, unsupported major versions, invalid paths, duplicate identities, and broken references shall fail with diagnostics rather than be ignored.
- Readers shall preserve supported unknown optional extension fields during a round trip.
- Migrations shall be ordered, deterministic, non-destructive to the source archive, and record their original and resulting versions.
- A canonical unpacked form shall mirror the archive content for Git-friendly review. Packing and unpacking identical content shall be deterministic apart from explicitly excluded container metadata.
- Normative numeric values use SI base units; display prefixes remain presentation data.
- Stochastic configurations store seed, distribution, sample count, model versions, and engine identity. [Source PDF, pp. 11, 31-32]

## Consequences

- Offline persistence, cloud storage, collaboration revisions, and simulation jobs share one content model.
- Archive parsing is a security boundary and requires schema, size, depth, path, and decompression limits.
- Format evolution requires compatibility fixtures and migration tests.

## Rejected alternatives

- **Database-only projects:** are not portable or offline-friendly.
- **An unversioned JSON document:** cannot support safe evolution or large/custom assets.
- **Opaque binary-only storage:** prevents useful source-control review.

## Compliance

Changing archive identity, manifest semantics, stable-ID rules, or migration guarantees requires a superseding ADR.
