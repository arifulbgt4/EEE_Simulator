# ADR-0002: Web Stack and Rust/WebAssembly Simulation Core

- Status: Accepted
- Date: 2026-07-11
- Decision owners: Project maintainers
- Related requirements: `REQ-004`, `REQ-008`, `REQ-009`, `REQ-011`, `REQ-012`, `REQ-017`, `REQ-019`, `REQ-033`, `REQ-034`, `REQ-036`

## Context

The browser must support a responsive schematic editor, visualization, hierarchy navigation, and simulation controls while numerical work remains off the main UI thread. The source brief recommends a compiled C/C++ or Rust core through WebAssembly and separate Workers for netlisting, analog solving, digital events, and waveform processing. [Source PDF, pp. 22-24]

## Decision

- The web application shall use Next.js and React with TypeScript.
- The native simulation core shall be written in Rust and compiled to WebAssembly.
- TypeScript owns product UI, interaction, orchestration, capability detection, and typed boundary adapters; numerically sensitive solver behavior belongs in Rust.
- The main browser thread shall run UI interaction only. Analog solving, digital scheduling, and waveform processing shall run in dedicated Workers; netlist preparation may use a separate Worker when benchmarks justify it.
- The project shall produce both single-threaded and threaded WebAssembly builds. Capability detection selects a supported build without changing project semantics.
- The threaded build requires the cross-origin isolation headers needed for shared memory. Deployments that cannot provide them shall use the single-threaded Worker build.
- Blocking waits and long simulation work are prohibited on the main browser thread. [Source PDF, pp. 23-24]
- Public boundaries between TypeScript and Rust shall use versioned, serializable contracts and SI base units.

## Consequences

- The core can be reused by browser Workers and eligible server-side runtimes without duplicating equations.
- Threading is an optimization path, not a correctness requirement.
- Browser compatibility tests must cover both WebAssembly builds and report capability-based degradation.
- UI code cannot directly depend on solver-internal memory layouts.

## Rejected alternatives

- **JavaScript-only numerical core:** does not provide the selected numerical-control and portability boundary. [Source PDF, p. 23]
- **Simulation on the main thread:** risks UI freeze and deadlock. [Source PDF, pp. 23-24]
- **Threaded-only WebAssembly:** would exclude otherwise supported deployments that lack cross-origin isolation.

## Compliance

Replacing the UI framework, simulation language, WebAssembly boundary, or mandatory Worker separation requires a superseding ADR.
