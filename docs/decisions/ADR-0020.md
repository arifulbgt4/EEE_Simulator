# ADR-0020: Generic Device and Vendor Variant Inheritance

- Status: Accepted
- Date: 2026-07-16
- Decision owners: Project maintainers
- Related requirements: `REQ-023`, `REQ-042`, `REQ-048`, `REQ-049`, `REQ-050`, `REQ-053`, `REQ-059`, `REQ-063`
- Extends: `ADR-0010`, `ADR-0013`, `ADR-0014`

## Context

Market catalogs contain many ordering codes whose behavior shares a generic family but differs in limits, timing, package, pin mapping, grade, or evidence. Duplicating a complete internal model for each code creates model explosion and drift. [Source PDF, pp. 6-8, 20, 26-27, 32-36]

## Decision

A vendor device or ordering-code revision shall inherit one exact generic-device revision and may apply only schema-authorized, dimensionally valid, bounded parameter overrides plus exact symbol, package, pin-profile, binding, metadata, provenance, license, and validation references. Each override records source evidence and trust state. Unknown, unit-incompatible, out-of-validity, or interface-changing overrides are rejected.

Vendor ingestion shall prefer manufacturer-approved models or measured evidence but shall preserve redistribution restrictions. A vendor record cannot claim coverage, accuracy, or release status beyond its generic base and its own evidence.

## Consequences

- Generic 74HC00 behavior can support distinct SN74HC00N and SN74HC00DR package variants without duplicating the internal gate model.
- Revision and lineage tools can explain every inherited and overridden value.
- Catalog counts represent actual records, not aspirational market coverage.

## Rejected alternatives

- **Copy a full model for each SKU:** causes inconsistent fixes and unreviewable scale.
- **Unbounded override maps:** can silently replace the inherited contract.

## Compliance

Changing inheritance semantics, permitting interface-changing overrides, or redistributing restricted vendor material requires a superseding ADR and license review.
